# Tentacles v1.4 — Hardening & Extensibility Pass

Repo: `kijukusanagi/tentacles-notion-manager`, branch `main`, currently v1.3 (last push 2026-03-19).

You are working on a docs-and-prompt repo. There is no application code. The "product" is `agent/system-prompt.md` (a Claude Project system prompt), `agent/config-template.json`, and the docs that support them. Two production forks exist that you cannot see — one at v1.3 with 9 databases, one at a `cl-1.0` fork off v1.2.1 with 13 databases — and both hit the same failure modes. This pass fixes those. It does NOT add features.

## Ground rules

- **Phase A is read-only.** No file edits, no branches, no commits until Phase A is delivered and approved.
- Label every claim **VERIFIED** (you read it in the repo), **ASSUMED** (inferred), or **UNKNOWN**.
- **Do not touch:** `brand/`, `LICENSE`, `notion-template/TEMPLATE_LINK.md`, the URL inside it, or anything that would require the hosted Notion template to change. v1.4 is schema-neutral: zero new properties, zero renamed properties, zero new databases in the base template.
- **Do not** rewrite the system prompt from scratch. Targeted patches only. The prompt has months of behavioral tuning in it that isn't documented anywhere.
- **Do not** invent a version bump beyond v1.4 or add migration registry entries for changes you didn't make.
- Stop for a diff review before applying any patch to `agent/system-prompt.md` or `agent/config-template.json`. Other files can be batched.

## PHASE A — Audit

### A1. Inventory and coherence

For every file: line count, self-declared version (exact line), and the version it *actually* reflects. Specifically confirm or refute:
- `examples/sample-config.json` declares v1.0 while the template is v1.3.
- `docs/project-plan.md` describes an 8-database system with a 3-step SETUP; `SETUP.md` has 6 steps.
- `docs/granular-dives-spec.md` labels its migration `v1.2 → v1.3` while the system prompt's registry labels it `v1.2.1 → v1.3`.
- `docs/v1.2-release-spec.md` publishes a Tickets `Type` enum without `Dive` and places `Hours Spent`/`Hours Estimated` under `optional_fields`, contradicting the v1.3 template.
- `CHANGELOG.md` and `UPGRADING.md` cover every hop: 1.0 → 1.1 → 1.2 → 1.2.1 → 1.3.

### A2. Mode detection and config trust

Read the Mode Detection section and the Operations Mode startup version check. Answer:
1. What is the exact file-matching rule? Does `config-template.json` match it? Would `tentacles-config-template-v1_3.json` (a renamed copy a user might upload) match it?
2. Is there any check that a matched config contains real IDs rather than `{PLACEHOLDER}` values before the agent enters Operations Mode?
3. Is there any check that the config's database IDs correspond to databases the agent can actually fetch?
4. What happens if two files match?
5. What happens if the config's `system_prompt_version` is a value not on the version line at all (e.g. `"2.1"`)?

### A3. Live-schema drift

The single most common production failure: the config says a property/enum/relation exists, Notion disagrees. Find every place the prompt tells the agent to trust the config for schema (enum values, property names, relation targets, DB count). Then find every place it tells the agent to fetch live schema first. Report the ratio and list the write paths that have no live-schema guard.

### A4. Hardcoded database count

Grep for `8 database`, `8 DBs`, `all 8`, `eight`, and the enumerated list of database names. Report every location across prompt, config template, docs, README, SETUP. This is the extensibility blocker — both forks added databases and had to patch every one of these by hand.

### A5. Project-knowledge kit vs repo docs

Classify every file as one of:
- **Operating kit** — belongs in a user's Claude Project knowledge (the agent reads it at runtime)
- **Repo doc** — for maintainers and curious users; should NOT be in project knowledge
- **Both / unclear**

Currently SETUP.md tells users what to upload. Report whether that list matches your classification, and whether any repo doc in project knowledge could mislead the agent (e.g. a release spec with a superseded schema block).

### A6. Onboarding friction

Walk `SETUP.md` and the Onboarding Mode section as a first-time user would. List every step that requires the user to know something the docs don't tell them, every step that could silently fail, and every place the promised time (5 minutes) is implausible. You will be handed a real friction log from a timed fresh setup to merge with this — leave a `## Friction log (external)` placeholder.

### A7. Deliverable

Single markdown report, sections A1–A6, ending with a **proposed v1.4 change list** — each item: file(s), one-line change, risk (does it alter agent behavior? yes/no). Stop. Wait for approval.

## PHASE B — Build (gated; do not start until Phase A is approved)

Target scope, subject to Phase A findings. Expect the approved list to be a subset.

### B1. Config trust hardening (system prompt + config template)
- Replace the `*-config-*.json` glob with an explicit marker: a top-level `"tentacles_config": true` key. Mode detection requires the key. Templates and examples do not carry it — add `"tentacles_config": false` to `config-template.json` and `sample-config.json` with a comment field explaining why.
- Add a **config validation step** at Operations Mode startup, before the version check: refuse to operate if any `_id` field matches `^\{[A-Z_]+\}$`; if more than one file carries the marker, stop and ask; if `system_prompt_version` is not in the known version list, warn once and name the known list.
- Add a **`doctor` behavior**: on "doctor", "check config", "health check config" — fetch every database in the config by data source ID, compare live properties/enums/relations to the config, report drift as a table, propose a config regeneration. Read-only. This is the reconciliation artifact both forks lack.

### B2. Live-schema-first rule (system prompt)
- One new Core Rule: before any write that sets a select/status value, a relation, or references a property by name, fetch the live data source schema for that database in the current session (cache per session is fine). Config is a hint, live schema is authority.
- Add the corollary that both forks learned the hard way: when altering a select column, re-declare the full option list — Notion drops unmentioned options.

### B3. Database extensibility (system prompt + config template + docs)
- Replace every hardcoded "8" with language driven by the config's `databases` map. The base template ships 8; the prompt operates on whatever the config lists.
- Add an `extensions` section to the config template: `{ "databases": [] }` where each entry has the same shape as a core database entry plus `"role"` (free text) and `"relations_to_tickets"` (property name on Tickets, or null). Document that extension DBs must reach Tickets within 2 hops or they are invisible to the intake layer.
- Add `docs/extending.md`: how to add a database, what the agent will and won't do with it, and the two-artifact rule (repo/config vs Notion template).
- Do NOT ship any specific extension DB in v1.4. Meetings and Suggested Tickets from the cl-1.0 fork are candidates for v1.5 as optional modules — note them in the roadmap only.

### B4. Docs reconciliation
- Fix every A1 finding. `sample-config.json` to v1.4 shape with the marker set false. Align the registry label in `granular-dives-spec.md`. Header on `v1.2-release-spec.md` marking its schema blocks historical.
- SETUP.md: state explicitly which files go into project knowledge (per A5 classification) and which do not. Add the marker requirement.
- `docs/project-plan.md`: either update to reflect reality or move to `docs/history/` with a one-line header. Don't leave it lying to people.

### B5. Version plumbing
- Bump to v1.4 in the prompt header line, the versioning paragraph, `config-template.json` (`version`, `system_prompt_version`, `changelog`), CHANGELOG.md, UPGRADING.md.
- Add `## v1.3 → v1.4` to the Migration Registry. Schema changes: none. Config changes: add `tentacles_config`, add `extensions`. Behavioral: config validation at startup, live-schema-first rule, doctor, extensible DB count.

### B6. Handoff
- Branch `v1.4-hardening`. Commits grouped by B-section, conventional prefixes matching the existing log (`v1.4: ...`, `docs: ...`).
- Final message: list of files changed, the exact `## v1.3 → v1.4` registry block, and a **fresh-setup test script** — the numbered steps a tester should follow, with the expected agent response at each checkpoint, so the timed setup run on v1.4 is comparable to the v1.3 baseline.
- Do not open a PR or push to `main`.
